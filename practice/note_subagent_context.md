# 学习笔记：子 Agent 的独立上下文与结果返回

> 原始材料（唯一依据）：「子 Agent 使用独立上下文处理子任务，并将最终文本返回父 Agent。」

---

## 一、核心概念

| 概念 | 含义 |
| --- | --- |
| 父 Agent | 发起委派、拥有当前对话上下文的一方 |
| 子 Agent | 接收子任务并独立完成的一方 |
| 独立上下文 | 子 Agent 拥有一套自己的上下文，不与父 Agent 共用对话历史 |
| 子任务 | 交给子 Agent 的一段明确、相对独立的工作 |
| 最终文本 | 子 Agent 回传给父 Agent 的产物形态是文本，且是"最终"结果 |

材料中可直接确认的三条事实：

1. 子 Agent **使用独立上下文**处理子任务。
2. 处理对象是**子任务**（父 Agent 拆分出去的工作单元）。
3. 返回物是**最终文本**，接收方是**父 Agent**。

补充说明（属于合理推论，非材料原文）：

- "独立上下文"意味着子 Agent 看不到父 Agent 的对话历史，因此任务描述必须自带目标、背景、约束和返回要求。
- 只回传"最终文本"，意味着子 Agent 的中间过程不会自动进入父 Agent 的上下文。
- 材料未规定同步/异步、返回格式、失败处理等实现细节，此处不作臆测。

---

## 二、运行流程与关键关系

```
父 Agent（持有完整对话上下文）
   │
   │  ① 委派：把子任务写成一段自包含的描述
   ▼
子 Agent（独立上下文，看不到父 Agent 的历史）
   │
   │  ② 在自己的上下文内处理子任务
   ▼
子 Agent 产出最终文本
   │
   │  ③ 回传：只把最终文本交给父 Agent
   ▼
父 Agent 拿到结果，继续自己的主线任务
```

三个关键关系：

1. **上下文是隔离的，不是共享的。** 父 Agent 上下文里的信息，子 Agent 默认不知道；反之子 Agent 的过程细节父 Agent 也默认不知道。
2. **信息只能靠"任务描述"和"返回文本"两个通道流动。** 通道很窄，所以两头都要写清楚。
3. **交换的是结论，不是过程。** 父 Agent 得到的是最终文本，需要时还要自行判断是否复核。

---

## 三、简短示例

场景：父 Agent 正在重构一个项目，顺带想知道仓库里有多少个 Python 文件。

- 委派（父 → 子）：
  「统计当前工作目录下所有 `.py` 文件的数量，只返回一个数字和文件清单，不需要解释过程。」
  —— 这句话必须自包含，因为子 Agent 的独立上下文里**没有**"我们正在重构项目"这段历史。
- 处理（子 Agent 内部）：子 Agent 在自己的上下文里查找、汇总。
- 返回（子 → 父）：
  「12 个：main.py、practice/s06_demo.py、……」
  —— 父 Agent 只收到这段最终文本，收不到子 Agent 中间尝试过的每一步。
  （注：以上文件数量与名称均为虚构的教学示例，不代表本仓库实际情况。）

对比一下就能看出机制：如果父 Agent 只写「帮我数数文件」，子 Agent 既不知道数哪里的文件、也不知道要什么格式，因为它没有父 Agent 的上下文可参考。

## 四、自测题

1. 为什么委派给子 Agent 的任务描述里，必须写清目标、背景、约束和返回要求，而不能像对同事那样只说"接着刚才的话题继续做"？
2. 子 Agent 返回后，父 Agent 拿到的内容与其内部执行过程有什么关系？由此推断，父 Agent 在采信结果前应当注意什么？
